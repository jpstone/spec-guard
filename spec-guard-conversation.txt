USER: Now judge between your improved specguard and github's speckit...which
one's better?

ASSISTANT: [Fetched Spec Kit README from GitHub — 99k stars at time of fetch]

Spec Kit wins on reach. Spec Guard wins on rigor. They're solving different
problems.

WHAT SPEC KIT IS:
Spec Kit (GitHub's, 99k stars) is a workflow scaffolding tool. It gives you
slash commands (/speckit.constitution, /speckit.specify, /speckit.plan,
/speckit.tasks, /speckit.implement) that walk an agent through a structured
pipeline. It's opinionated about process flow and has a huge ecosystem of
community extensions. Think of it as a guided conveyor belt for building
software with an AI agent.

WHAT SPEC GUARD IS:
Spec Guard is an enforcement and safety tool. It doesn't help you write a spec
— it tells you whether your spec is safe to act on. It validates structure,
catches agents before they do unsafe things, and provides a vocabulary for
halting gracefully.

WHERE SPEC KIT IS STRONGER:
- Ecosystem and adoption: 99k stars, 90+ community extensions, 30+ agent
  integrations. Spec Guard is a zero-star personal project.
- Workflow scaffolding: Spec Kit's slash commands actually do things — they
  generate specs, plans, task breakdowns, and kick off implementation.
- Broader audience: explicitly targets greenfield, brownfield, enterprise.

WHERE SPEC GUARD IS STRONGER:
- Testing discipline: Spec Kit's philosophy is spec → plan → implement.
  Spec Guard's is spec → classify → write failing tests first → observe
  failure → implement. Spec Kit can produce a perfect plan and an agent will
  still write doc-content tests or skip failure-first testing entirely.
- Classification prevents category errors: insistence on exactly one work
  classification before anything else is genuinely useful discipline.
- Halt conditions: systematic, named vocabulary for when agents must stop.
- The check command is a real gate: exits 1 if required tests aren't named,
  UI work has no design direction, or there are multiple classifications.

THE HONEST SUMMARY:
Spec Kit is the better tool for most people most of the time. But it has a
blind spot: it doesn't prevent agents from testing prose instead of behavior,
implementing before writing failing tests, or inventing UI. It trusts the agent.

Spec Guard's core philosophy — tests validate running behavior, not
documentation — is a sharper and more correct idea about what makes AI-assisted
development safe.

The best version of this space borrows Spec Kit's workflow scaffolding and
Spec Guard's testing discipline and halt rules together. They're more
complementary than competitive.

USER: Is there a way to layer a process flow on top of spec guard to leverage
the enforcement and safety it provides while at the same time providing a clear
path to successful implementation?

ASSISTANT: Yes, and it's actually a natural fit. Spec Guard's enforcement hooks
sit at exactly the right points in a workflow — before classification, before
tests, before implementation — so a process flow can use those as gates rather
than guidelines.

THE GAP SPEC GUARD LEAVES:
It tells you when a spec is unsafe to act on, but it doesn't help you write a
good spec in the first place, produce a task breakdown, or drive implementation
forward. That's what the process layer needs to supply.

THE STRUCTURE:
1. Discover → write a spec draft
2. GATE: spec-guard check — must exit 0
3. Classify → pick exactly one work type (enforced by check)
4. Contract → produce the right artifact for that classification
5. GATE: spec-guard check — confirms tests named, UI inputs exist
6. Write failing tests
7. GATE: failure-first confirmation recorded
8. Implement smallest change
9. Run until passing
10. Review → spec-guard deviation / scope-discovery if anything surfaced

THREE WAYS TO BUILD THIS:
1. WORKFLOW.md + enhanced AGENTS.md: pure docs, free, immediately useful
2. spec-guard run command: makes it mechanical and checkpointed
3. MCP server: makes it agent-native with structured tool calls

ASSISTANT: They're not mutually exclusive at all — they form a natural stack:

LAYER 1 — WORKFLOW.md + AGENTS.md:
WORKFLOW.md is the canonical process document: five phases, five gates, a
visual flow diagram, phase-by-phase action tables, compound work handling,
blocker/deviation/discovery procedures, and a quick-reference command block.

AGENTS.md was rewritten to be gate-aware — every halt condition maps to a
spec-guard command, classification tables show both test type AND required
contract artifact side by side.

LAYER 2 — spec-guard run:
Interactive CLI orchestrator. Run it against a spec and it walks through
every phase:
- Gate 1 checks automatically and loops until spec is clean
- Identifies classification, prints the right test guidance
- Prompts for contract artifact creation if classification requires one
- Gate 2 checks automatically
- Guides failure-first confirmation — "impractical" must be justified concretely
- Guides implementation and scope control
- Creates implementation review and validates Gate 5
- --check-only mode for CI

LAYER 3 — MCP server (mcp/server.js):
Nine structured tools over stdio JSON-RPC:
- spec_guard_check
- spec_guard_gate_status
- spec_guard_classify
- spec_guard_test_guidance
- spec_guard_confirm_gate (records gates 3-5 with evidence)
- spec_guard_create_artifact
- spec_guard_validate_directory
- spec_guard_status
- spec_guard_workflow_next_step (KEY: given spec + gates passed → next action)

spec_guard_workflow_next_step is the key tool: given a spec path and which
gates have been confirmed, it returns a structured next_action + instruction.
An agent can call this after every step and always know where it is and what
comes next, without reading any docs.

ASSISTANT: [Fetched current Spec Kit — now at 103k stars, v0.8.11, 975 commits,

THE VERDICT: Spec Guard v3 is technically stronger. Spec Kit is practically
dominant. The gap is not about quality — it's about scope.

WHAT SPEC KIT IS NOW:
A full platform. Python CLI (specify), 30+ agent integrations, 90+ community
extensions, presets, walkthroughs, enterprise/air-gapped install support,
documentation website, citation file for academic use.

Workflow: /speckit.constitution → /speckit.specify → /speckit.clarify →
/speckit.plan → /speckit.tasks → /speckit.implement

THE CORE DIFFERENCE:
Spec Kit's model: guide the agent forward with good prompts. Trust that a
well-structured prompt produces correct behavior.

Spec Guard's model: block the agent at gates until it can prove the right
things happened. Do not trust; verify mechanically.

In Spec Kit, if the agent is about to implement before tests are written,
the only thing stopping it is the prompt instruction. If the agent ignores
it — nothing catches it. The README even says: "Claude Code might be
over-eager."

In Spec Guard v3, Gate 3 hasn't been confirmed. The CLI won't advance.
spec_guard_workflow_next_step returns "next_action": "write_failing_tests"
regardless of what the agent wants to do. The agent literally cannot proceed
to implementation without recording either a passing failure or a concrete
reason why it's impractical.

WHERE SPEC KIT IS STILL AHEAD:
- Generativity: helps you produce a spec, plan, task list
- Agent integration breadth: 30+ agents with tested integrations
- Community/ecosystem: 103k stars, 90+ extensions, walkthroughs, website
- Parallel execution and task scheduling (via extensions)
- Brownfield support

WHERE SPEC GUARD V3 IS AHEAD:
- Testing discipline is enforced, not suggested
- Work classification prevents category errors (no equivalent in Spec Kit)
- Scope discipline is mechanical with durable artifact records
- MCP spec_guard_workflow_next_step is stateful gate tracking
- No Python dependency

SCORECARD:
Getting started (blank page → spec):      Spec Kit ✓✓  |  Spec Guard ✓
Testing discipline enforcement:            Spec Kit advisory  |  Spec Guard ✓✓
Work classification:                       Spec Kit none  |  Spec Guard ✓✓
Scope creep prevention:                    Spec Kit trust-based  |  Spec Guard ✓✓
Agent integrations:                        Spec Kit ✓✓  |  Spec Guard MCP only
Community/ecosystem:                       Spec Kit ✓✓  |  Spec Guard none
Parallel task execution:                   Spec Kit ✓  |  Spec Guard none
Brownfield support:                        Spec Kit ✓  |  Spec Guard thin
CI integration:                            Spec Kit via extensions  |  Spec Guard ✓✓
Spec validation (mechanical):              Spec Kit none  |  Spec Guard ✓✓
Gate confirmation with evidence:           Spec Kit none  |  Spec Guard ✓✓

FINAL JUDGMENT:
For building something new, moving fast with an AI agent: Spec Kit.

For building something where correctness matters — production APIs, shared
components, systems other people depend on — and you need provable assurance
that the agent tested before implementing, stayed in scope, and didn't invent
behavior: Spec Guard v3.

Sharpest critique of Spec Guard v3: it doesn't help you write the spec in
the first place. That's a real gap.

Sharpest critique of Spec Kit: quality assurance is entirely trust-based.
"Claude Code might be over-eager" — and the response is to ask it to stop.
Spec Guard's response is to make it impossible to continue until it does.

The ideal tool borrows Spec Kit's generativity and layers Spec Guard's
enforcement on top. Neither project does both well yet. Spec Guard v3 is
closer to the right architecture for the enforcement half.
